# 戴夫突围 v0.1 详细测试用例

## 文档职责

本文档把 `docs/development/acceptance-standard.md` 中的 v0.1 验收标准转成可执行、可观察、可复核的测试用例。

本文档只写测试设计和证据要求，不写产品实现，不改验收标准，不替 `spec/游戏机制.md`、`spec/视觉规格.md` 或素材文档另立口径。

## 依据

- 验收标准：`docs/development/acceptance-standard.md`
- v0.1 范围：`spec/v0.1-戴夫突围.md`
- 玩法和数值事实源：`spec/游戏机制.md`
- 视觉事实源：`spec/视觉规格.md`
- 素材边界：`assets/README.md`、`assets/sprites/README.md`

## 测试入口规划

当前用例按下面几类入口设计。这里是测试要求，不假定这些脚本或参数已经存在；主 Agent 后续应按本文档补齐对应验证入口。

| 入口 | 用途 | 需要补齐的能力 |
| --- | --- | --- |
| Godot headless smoke | 验证工程可打开、主场景可加载、运行时无致命报错 | 能在无窗口模式启动项目、加载 `scenes/Main.tscn`、运行指定秒数、输出日志 |
| 固定随机种子运行 | 验证同种子同输入可复现 | 支持传入 seed、调试参数、输入脚本或录制输入，并导出状态快照 |
| 状态快照导出 | 验证玩法数值、波次、对象数量、升级层数、胜负状态 | 任意关键时刻导出 JSON 或等价结构化文件 |
| 调试快速流程 | 快速进入升级、胜利、失败、指定波次和技能冷却场景 | 支持 `upgrade`、`victory`、`failure`、`wave`、`combat_pressure`、`skills_ready` 等场景参数，不改变正常模式口径 |
| 真实窗口截图和帧序列 | 验证 HUD、升级弹窗、结算页、方向动画、VFX 和调试辅助层限制 | 能保存 1920x1080 真实运行截图、连续帧或短录屏，并保留文件名和场景说明 |
| 人工视觉复核 | 验证体感可读性、画面基准对照和整体成型 | 至少 1 名未参与实现的复核者，按本文档记录观察结论 |

## 证据目录建议

每轮正式验收建议把证据放在 `reports/v0.1-acceptance/<YYYYMMDD-HHMM>/`。如果主 Agent 后续指定别的报告目录，以主 Agent 指定为准。

证据至少包括：

- `logs/`：headless、窗口运行、报错扫描日志。
- `snapshots/`：状态快照 JSON。
- `screenshots/`：正常战斗、升级弹窗、胜利或失败结算、必要的调试辅助层截图。
- `frames/` 或 `videos/`：连续帧或短录屏。
- `visual-review.md`：人工视觉复核记录。
- `coverage.md`：本轮执行的用例、覆盖 AC、通过和失败项。

正式截图文件名必须能区分正常画面和调试辅助层，例如：

- `combat_hud_normal.png`
- `upgrade_modal_normal.png`
- `result_victory_normal.png`
- `combat_debug_ranges_enabled.png`

## 通用前置条件

除非单个用例另有说明，默认前置条件如下：

- 使用当前仓库根目录（包含 `project.godot` 的目录）。
- 使用 Godot 4.x 运行项目。
- 正常模式不启用调试辅助层。
- 设计视口按 1920x1080 验证视觉布局。
- 玩法数值按 `spec/游戏机制.md` 的 v0.1 数值口径验证。
- 运行时素材边界按 `assets/README.md` 和 `assets/sprites/README.md` 验证。

## TC-RUN-01 工程启动与主场景加载

目的：确认项目本身能作为 Godot 4.x 工程打开，主场景能直接启动。

覆盖 AC：AC-RUN-01、AC-RUN-02

前置条件：

- 仓库根目录存在。
- Godot 4.x 命令行可用。

操作步骤：

1. 在仓库根目录运行 headless smoke，加载项目并启动主场景。
2. 记录 Godot 版本、项目路径、主场景路径。
3. 运行至少 10 秒游戏时间后退出。
4. 扫描控制台日志和 Godot 日志。

通过标准：

- 根目录包含 `project.godot`。
- 项目主场景为 `scenes/Main.tscn`。
- 主场景能启动并进入可运行状态。
- 日志中没有脚本解析错误、资源加载错误或运行时致命错误。

证据产物：

- headless 运行日志。
- Godot 版本记录。
- 主场景路径记录。

## TC-RUN-02 运行时素材引用边界

目的：确认运行时没有把源素材目录或禁止路径接入游戏。

覆盖 AC：AC-RUN-03、AC-UI-07、AC-UI-08、AC-UI-10

前置条件：

- 项目已具备可扫描的 Godot 场景、脚本和资源引用。
- 主 Agent 已补资源引用扫描工具，或提供等价的 `rg`/资源清单扫描步骤。

操作步骤：

1. 扫描 `.tscn`、`.tres`、`.gd`、项目配置和资源清单中的 `res://` 引用。
2. 检查运行时引用是否只指向允许接入的 `assets/sprites/` 和 `assets/audio/sfx/`。
3. 单独检查是否引用 `assets/source/`、`.import` 文件、原始参考大图作为最终 UI 或 VFX。
4. 检查核心 UI 是否引用 `assets/sprites/ui/runtime/` 中的运行时 UI 资产，或由这些资产建出的 `.tres`。

通过标准：

- 运行时素材没有引用 `assets/source/`。
- Godot 代码和场景没有引用 `.import` 文件。
- 核心 UI 不主要依赖默认控件、纯色框、`draw_rect`、`draw_line`、`draw_circle` 或单色 `StyleBoxFlat` 模拟。
- 升级卡、HUD 主框、结算面板、暂停面板和提示横幅能追溯到运行时 UI 资产或对应 `.tres`。
- painted 总图和 reference crop 只作为参考或对照证据，不直接贴成最终 UI。

证据产物：

- 资源引用扫描报告。
- UI runtime 资产引用清单。
- 发现违规引用时的文件路径和行号。

## TC-RUN-03 模块边界与数值集中管理复核

目的：确认核心规则没有混写进 UI、动画或一次性调试脚本，公共数值有唯一口径。

覆盖 AC：AC-RUN-04、AC-RUN-05、AC-RUN-06、AC-PERF-05

前置条件：

- 项目已有实现代码。
- 主 Agent 提供代码结构说明或模块清单。

操作步骤：

1. 只读检查输入、战斗、刷怪、升级、结算、音效和调试观测入口对应模块。
2. 检查波次、升级、豌豆、敌人、音效事件、数量上限等公共数值是否从集中配置或等价唯一口径读取。
3. 抽查 UI、动画和调试脚本，确认其中没有承载主要玩法规则。
4. 检查 v0.1 非目标内容是否没有进入运行入口和主流程。
5. 检查调试加速、截图、帧序列和状态快照是否只用于辅助验证，不能改变正常模式玩法结果。

通过标准：

- 核心系统职责清楚，可追溯到独立模块或清晰的脚本边界。
- 公共数值集中管理，和 `spec/游戏机制.md` v0.1 数值口径一致。
- 正常运行入口不包含存档、账号、排行榜、商店、背包、天赋树、第二张地图、随机地图、多人、后端、复杂 Boss、新增豌豆种、新增敌人技能、移动端适配或发布打包优化。
- 调试参数只改变进入状态或验证速度，不改变正常模式口径。

证据产物：

- 模块边界检查记录。
- 数值来源清单。
- 非目标内容扫描记录。

## TC-OBS-01 固定随机种子可复现

目的：确认同一个种子、同一组输入和同一套调试参数下，关键状态推进可复现。

覆盖 AC：AC-OBS-01

前置条件：

- 主 Agent 补齐固定随机种子入口。
- 主 Agent 补齐输入脚本或录制输入回放能力。
- 主 Agent 补齐状态快照导出。

操作步骤：

1. 使用固定 seed A、固定输入序列和相同调试参数运行一局到第 2 波中段。
2. 在 0:20、0:45、1:05 导出状态快照。
3. 使用同样条件重复运行一次。
4. 对比两次快照中的关键字段。
5. 更换 seed B 运行一次，确认快照允许出现符合随机逻辑的差异。

通过标准：

- 同 seed、同输入、同调试参数下，关键状态一致或在已定义容差内一致。
- 不同 seed 下允许刷怪位置、升级抽取等随机结果不同。
- 复现能力不依赖人工肉眼判断。

证据产物：

- 两组 seed A 快照。
- 一组 seed B 快照。
- 快照对比报告。

## TC-OBS-02 状态快照字段完整性

目的：确认任意关键时刻能导出验收标准要求的状态字段。

覆盖 AC：AC-OBS-02

前置条件：

- 主 Agent 补齐状态快照导出入口。

操作步骤：

1. 正常模式启动新一局，导出初始状态快照。
2. 战斗中导出状态快照。
3. 升级弹窗出现时导出状态快照。
4. 解锁熔岩豌豆后导出状态快照。
5. 结算页导出状态快照。

通过标准：

- 每份快照至少包含：戴夫血量、最大血量、当前波次、波次进度、游戏时间、游戏状态、场上敌人数、场上豌豆弹数、场上毒液数、击杀数、当前经验、升级所需经验、升级次数、已解锁武器、各升级层数。
- 字段名称稳定，数值类型明确。
- 快照能用于自动断言，不只是一段给人看的文本。

证据产物：

- 多阶段状态快照 JSON。
- 字段完整性检查报告。

## TC-OBS-03 快速进入关键流程

目的：确认升级、胜利、失败流程不需要每次完整打满一局才能检查。

覆盖 AC：AC-OBS-03

前置条件：

- 主 Agent 补齐快速进入升级、胜利、失败三个流程的调试入口。

操作步骤：

1. 使用调试入口进入即将升级状态，触发升级三选一。
2. 使用调试入口进入即将胜利状态，推进到胜利结算。
3. 使用调试入口进入即将失败状态，推进到失败结算。
4. 分别导出状态快照、截图和日志。
5. 检查这些入口是否只影响验证路径，不改变正常模式规则。

通过标准：

- 三个关键流程都能稳定进入。
- 进入后状态和 UI 与正常流程一致。
- 调试入口默认关闭，只能通过显式参数启用。

证据产物：

- 三类流程的运行日志。
- 三类流程的状态快照。
- 升级、胜利、失败截图。

## TC-OBS-04 正式视觉证据保留

目的：确认正式验收有真实运行截图和动态证据，不只靠日志。

覆盖 AC：AC-OBS-04、AC-OBS-05、AC-UI-11

前置条件：

- 主 Agent 补齐真实窗口截图或帧序列捕获入口。
- 正常模式默认关闭调试辅助层。

操作步骤：

1. 正常模式运行游戏，保存战斗 HUD 截图。
2. 触发升级弹窗，保存升级弹窗截图。
3. 触发胜利或失败结算，保存结算页截图。
4. 保存一段能看到战斗动态的连续帧或短录屏。
5. 检查正式截图中是否出现调试辅助痕迹。
6. 如需检查碰撞、范围、刷怪区等调试信息，另开显式调试入口截图，并在文件名和报告中标明。

通过标准：

- 至少有战斗、升级弹窗、胜利或失败结算三类真实运行截图。
- 至少有一段连续帧或短录屏能看到战斗动态。
- 正式截图没有碰撞半径圈、攻击半径圈、激活范围圈、刷怪区矩形、地图边界矩形、敌人类型文字标签、AI 状态标签、对象池标记、坐标标记或开发者辅助线。
- 调试辅助层截图与正式截图明确分开。

证据产物：

- 三类正式截图。
- 连续帧或短录屏。
- 调试辅助层截图记录，若本轮使用。

## TC-INPUT-01 移动、镜头和地图边界

目的：确认玩家输入、移动速度方向一致性、镜头跟随和地图边界可用。

覆盖 AC：AC-INPUT-01、AC-INPUT-02、AC-MAP-01、AC-MAP-02、AC-MAP-03、AC-MAP-05、AC-MAP-06

前置条件：

- 主 Agent 补齐输入脚本或人工操作记录模板。
- 主 Agent 补齐位置和速度快照字段。

操作步骤：

1. 在正常模式下分别按 W、A、S、D 和方向键移动。
2. 分别按斜向组合键移动，例如 W+D、W+A、S+D、S+A。
3. 导出单轴和斜向移动速度快照。
4. 移动到地图四周边界，观察是否能走出地图视觉边界或进入不可读区域。
5. 截取不同地图位置的正常画面。
6. 检查镜头只显示地图一部分，Camera2D zoom 位于 0.8 到 1.2。

通过标准：

- WASD 和方向键都能稳定移动戴夫。
- 上下左右和斜向移动稳定，斜向移动不能明显快于单轴移动。
- 镜头跟随戴夫移动。
- 玩家不能走出地图视觉边界或进入不可读地图外区域。
- 游戏使用一张固定户外大地图，不做地图切换、随机地图、迷宫、钥匙门或复杂探索。
- 地图明显大于屏幕，一屏约看到 `full_outdoor_map_painted_4096x2305.png` 整图四分之一。
- 地图边界通过围栏、树墙、石墙、水面或其他视觉方式表达清楚。
- 玩家出生点和刷怪区附近可读，不过度拥挤。

证据产物：

- 输入记录。
- 移动速度快照。
- 地图边界截图。
- Camera2D zoom 和视口记录。

## TC-INPUT-02 自动攻击与升级选择交互

目的：确认玩家不需要手动瞄准，升级三选一可点击且选择后恢复战斗。

覆盖 AC：AC-INPUT-03、AC-INPUT-04、AC-INPUT-07、AC-GROWTH-05

前置条件：

- 主 Agent 补齐快速进入升级流程入口。
- 场上可生成敌人。

操作步骤：

1. 正常模式下只移动戴夫，不点击攻击键、不操作鼠标瞄准。
2. 观察豌豆是否从戴夫附近自动发射并攻击敌人。
3. 使用快速入口触发升级三选一。
4. 分别点击三个升级卡位置，至少覆盖三次运行。
5. 选中升级后导出快照，并继续观察战斗。

通过标准：

- 玩家无需手动瞄准或主动攻击。
- 豌豆会自动从戴夫附近发射并攻击敌人。
- 升级三选一每次出现 3 个升级项，除非可选项不足 3 个。
- 玩家能用鼠标点击任意可选升级项。
- 选中后升级立即生效，升级 UI 关闭，战斗恢复。
- 升级弹窗期间战斗暂停，升级 UI 仍可点击。

证据产物：

- 自动攻击帧序列。
- 升级点击前后状态快照。
- 三个卡片点击记录。

## TC-INPUT-03 暂停与恢复

目的：确认 Esc 或 P 暂停恢复可用，暂停时战斗实体停止但 UI 可操作。

覆盖 AC：AC-INPUT-06

前置条件：

- 战斗中至少存在敌人、豌豆弹、经验或毒液中的任意两类动态对象。
- 状态快照包含游戏时间和对象位置。

操作步骤：

1. 正常战斗中按 Esc 暂停。
2. 暂停后等待真实时间 3 秒，连续导出状态快照。
3. 检查战斗计时、刷怪、敌人、弹体和经验移动是否停止。
4. 使用 UI 或再次按 Esc 恢复。
5. 用 P 重复一次暂停和恢复。

通过标准：

- Esc 和 P 都能暂停和恢复游戏。
- 暂停期间战斗计时不推进。
- 刷怪、敌人、豌豆弹、毒液和经验移动停止。
- 暂停 UI 或恢复操作仍可用。
- 恢复后战斗继续推进。

证据产物：

- 暂停前、中、后状态快照。
- 暂停界面截图。
- 输入操作记录。

## TC-INPUT-04 结算重开

目的：确认胜利和失败结算页都能重开，重开后回到新一局初始状态。

覆盖 AC：AC-INPUT-05、AC-LOOP-06

前置条件：

- 主 Agent 补齐快速进入胜利和失败流程入口。
- 状态快照包含初始状态、结算状态和重开后状态。

操作步骤：

1. 使用调试入口进入胜利结算。
2. 点击重开入口，导出重开后快照。
3. 使用调试入口进入失败结算。
4. 点击重开入口，导出重开后快照。
5. 对比两次重开后状态与新局初始状态。

通过标准：

- 胜利结算页提供重开入口。
- 失败结算页提供重开入口。
- 点击重开后回到新一局初始状态。
- 重开后戴夫血量、波次、敌人、弹体、经验、升级层数、已解锁武器和计时都重置。

证据产物：

- 胜利结算与重开快照。
- 失败结算与重开快照。
- 重开前后截图。

## TC-LOOP-01 一局完整闭环

目的：确认从开始到结束形成完整一局，而不是孤立功能演示。

覆盖 AC：AC-LOOP-01、AC-LOOP-03、AC-LOOP-04、AC-SHAPE-05

前置条件：

- 正常模式可运行。
- 固定 seed 验收用例已准备。

## TC-COMBAT-01 三种豌豆机制差异

目的：确认三种豌豆的机制和表现都不同，且各自按事实源数值运行。

覆盖 AC：AC-COMBAT-02、AC-COMBAT-03、AC-COMBAT-04、AC-COMBAT-05、AC-COMBAT-06、AC-SHAPE-02

操作步骤：

1. 开局状态确认只拥有橘豌豆。
2. 在戴夫周围布置多个不同距离敌人，观察橘豌豆是否朝发射时最近敌人直线扑击。
3. 解锁熔岩豌豆后布置密集敌群和稀疏敌人，观察熔岩豌豆是否飞向敌人密集处并接近后范围爆炸消失。
4. 解锁西瓜豌豆后布置多名近身敌人，观察西瓜豌豆是否沿短弧线或回旋弹道飞行，并可命中多个敌人。

- 橘豌豆开局即拥有。

- 复核者能用自己的话说出三种豌豆的大致差异。

## 本轮新增回归用例

本节记录用户本轮提出的平衡和技能变更。它们是产品回归要求，不修改 `docs/development/acceptance-standard.md` 的 AC 编号或通过口径；若后续正式纳入 v0.1 验收，应先更新验收标准和事实源。

### TC-REG-01 刷怪密度与开局发射节奏

目的：确认僵尸数量下降、开局橘豌豆发射频率略有提升，且没有突破既有对象上限。

前置条件：

- 使用同一固定 seed，分别运行基线版本和变更版本；若没有基线，使用集中配置中的变更前后数值记录作为对照。
- 从新局开始，前 30 秒不选择升级、不使用主动技能。
- 状态快照包含 `game_time`、`spawn_count`、`active_enemies`、`peas_fired`、`orange_fire_cooldown` 和 `pea_count`。

操作步骤：

1. 运行 0 到 30 秒，每 5 秒导出一次快照。
2. 统计每个 5 秒窗口刷新的僵尸数量和橘豌豆发射数量。
3. 对比变更前后的刷怪数量和橘豌豆发射间隔；记录配置来源和实际观测值。
4. 在高压波次继续运行，检查敌人、豌豆、毒液和经验球仍遵守既有上限。

通过标准：

- 变更版本的前 30 秒刷怪量相对基线降低，或达到产品负责人指定的目标密度；不能用降低敌人上限来伪造“密度降低”。
- 橘豌豆开局即可发射，平均发射间隔相对基线略短，且发射计数与冷却配置一致。
- 发射频率提升不能导致豌豆弹超过 `TC-PERF-01` 的上限，也不能造成连续致命报错或明显卡顿。

证据产物：

- 同 seed 的基线/变更快照对比。
- 刷怪和发射统计表。
- 配置来源和对象上限检查记录。

### TC-REG-02 熔岩豌豆扩大爆炸范围

目的：确认熔岩豌豆爆炸半径扩大后能稳定命中更大范围的敌人，并保留一次爆炸后消失的机制。

前置条件：

- 使用 `skills_ready` 或等价调试入口解锁熔岩豌豆。
- 能生成至少一组密集敌人和一名位于旧半径外、位于新半径内的对照敌人。
- 快照或战斗事件日志包含 `pea_type`、`explosion_center`、`explosion_radius`、`hit_enemy_ids`、`damage_events` 和 `pea_removed`。

操作步骤：

1. 让熔岩豌豆在密集敌群附近触发爆炸，保存爆炸前后连续帧。
2. 记录爆炸半径和命中的敌人 ID；特别标记旧半径外、新半径内的对照敌人。
3. 检查熔岩豌豆是否只触发一次爆炸，随后从活动豌豆列表移除。
4. 重复 5 次，检查相同布局下命中结果稳定。

通过标准：

- 运行时爆炸半径来自集中配置，且大于变更前口径；测试记录必须写出实际数值，不能只凭截图判断“变大”。
- 新半径内的对照敌人受到一次范围伤害，半径外敌人不应被误伤。
- 爆炸特效清晰可见，熔岩豌豆爆炸后不会继续飞行或重复结算伤害。
- 扩大范围不能突破敌人数量、日志错误和帧时间约束。

证据产物：

- 爆炸连续帧或短录屏。
- 爆炸事件日志和命中 ID 列表。
- 旧半径/新半径及边界命中对照表。

### TC-REG-03 技能一：全场冰冻

目的：确认右下角第一个圆形技能图标、开局冷却、25 秒冷却和全场僵尸冻结 3 秒均正确。

前置条件：

- 正常战斗画面无调试辅助层。
- 状态快照包含 `skill_1_cooldown_remaining`、`skill_1_ready`、`frozen_until`、`frozen_enemy_count`、`game_time` 和敌人位置/速度。
- 事件日志包含 `skill_1_pressed`、`skill_1_started`、`skill_1_finished` 和 `skill_1_rejected_cooldown`。

操作步骤：

1. 新局开始立即截取右下角技能栏，确认第一个圆形图标可见但处于冷却遮罩状态，剩余冷却约 25 秒。
2. 冷却结束后点击/按键发动技能一，记录发动时刻和当时场上所有僵尸数量。
3. 在发动后 0、1.5、2.9、3.1 秒分别导出快照，比较冻结敌人的位置、速度和攻击行为。
4. 冷却未结束时再次触发，确认不会重复发动；冷却结束后再次发动，确认可复用。

通过标准：

- 第一个圆形图标固定在右下角，不随 Camera2D 漂移，不遮挡主要 HUD 或战斗信息。
- 技能一开局进入冷却，冷却时长为 25 秒；未就绪时视觉上明确禁用，输入会被拒绝且不消耗额外状态。
- 发动后全场现有僵尸冻结 3 秒：位置不推进、不造成接触伤害、不发射远程毒液；3 秒后统一恢复。
- 技能发动、冷却开始、冷却结束和再次发动均有可观察事件日志；正常画面有短暂冰冻反馈。

证据产物：

- 开局、冷却中、就绪和发动后的 HUD 截图。
- 0/1.5/2.9/3.1 秒状态快照。
- 技能事件日志和输入拒绝记录。

### TC-REG-04 技能二：八方向双发射

目的：确认右下角第二个圆形技能图标、开局 40 秒冷却，以及发动时 8 个方向各发射 2 个豌豆。

前置条件：

- 使用 `skills_ready` 入口或等待冷却结束。
- 状态快照包含 `skill_2_cooldown_remaining`、`skill_2_ready`、`skill_2_projectile_ids`、`skill_2_direction_counts` 和 `peas_fired`。
- 事件日志包含 `skill_2_pressed`、`skill_2_started`、`skill_2_finished` 和 `skill_2_rejected_cooldown`。

操作步骤：

1. 新局开始立即截取右下角技能栏，确认第二个圆形图标可见且处于 40 秒冷却。
2. 冷却结束后发动技能二，保存发动瞬间连续帧和快照。
3. 按方向向量将新增豌豆归类为上、下、左、右及四个对角方向，统计每个方向数量。
4. 冷却未结束时重复输入，确认不会生成额外豌豆；冷却结束后再次发动，确认技能可复用。

通过标准：

- 第二个圆形图标固定在右下角，与第一个图标间距稳定且不重叠。
- 技能二开局进入冷却，冷却时长为 40 秒；未就绪时输入被拒绝。
- 每次成功发动恰好生成 16 个豌豆：8 个方向各 2 个；方向计数不能因帧率或敌人位置改变。
- 技能生成的豌豆沿各自方向正常飞行并遵守全局豌豆上限；技能发动和冷却状态可从日志、快照及画面三方核对。

证据产物：

- 开局冷却和技能发动 HUD 截图。
- 16 个豌豆的方向计数快照及连续帧。
- 技能事件日志、冷却拒绝记录和对象上限检查。

### TC-REG-05 双技能联动与暂停

目的：确认两个主动技能的冷却计时遵循游戏时间，暂停期间不偷跑，且技能效果不会破坏升级/结算流程。

操作步骤：

1. 技能一、技能二均就绪时连续发动，记录两个冷却计时器和各自事件。
2. 发动技能一后立即暂停 3 秒真实时间，比较暂停前后 `game_time`、`frozen_until` 和两个剩余冷却。
3. 恢复后等待技能一结束，确认僵尸恢复；再等待技能二就绪并发动，确认仍生成 16 个豌豆。
4. 在技能效果期间触发升级弹窗和结算快速流程，检查 UI 层级、冻结状态和结算状态没有互相卡死。

通过标准：

- 暂停期间游戏时间、技能冷却、冻结剩余时间和战斗实体均停止推进。
- 恢复后冷却和冻结倒计时从暂停点继续，不发生跳秒或重复触发。
- 技能效果结束、升级、胜利/失败和重开均能回到可运行状态；重开后两个技能都恢复初始冷却。

证据产物：

- 暂停前、中、后快照。
- 双技能联动事件日志。
- 升级和结算流程截图。

### TC-REG-07 药水刷新、拾取与受击音效分流

目的：确认药水在 60/120/180 秒各刷新一瓶，戴夫接触后恢复 10 点并消失并播放 `potion_drink`；毒液命中只播放 `venom_hit`，僵尸接触才播放 `player_hurt`。

操作步骤：

1. 使用固定 seed 运行新局，在 60、120、180 秒分别记录 `potions` 数量和药水位置，确认每个时间点只新增一瓶。
2. 让戴夫接触药水，记录血量变化和药水数量；确认血量增加 10 点且药水从场上移除，血量不超过 100。
3. 分别让毒液和僵尸接触戴夫，检查音效事件计数：毒液命中只增加 `venom_hit`，僵尸接触增加 `player_hurt`。

通过标准：

- 三个时间点各生成一瓶随机位置药水；重开后刷新计时和药水状态归零。
- 药水拾取一次只恢复 10 点并立即消失。
- 毒液伤害不触发 `player_hurt`；僵尸接触伤害仍触发 `player_hurt`。

证据产物：

- 60/120/180 秒状态快照。
- 拾取前后血量与药水数量快照。
- `potion_drink`、`venom_hit`、`player_hurt` 音效事件计数记录。
