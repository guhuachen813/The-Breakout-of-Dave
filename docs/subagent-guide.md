# 子 Agent 使用说明

这个文档说明在本项目里什么时候应该开子 Agent、怎么开、怎么验收。

核心原则：主 Agent 负责方向、拆分、整合和最终判断；子 Agent 只负责边界清楚、输入明确、结果可检查的小任务。

## 什么时候可以开子 Agent

适合开子 Agent 的情况：

- 任务可以拆成互不影响的小块。
- 每个小块都有明确输入、明确目标和明确完成标准。
- 子 Agent 只需要查看或修改少量文件。
- 子 Agent 的结果可以通过文档、测试、日志、截图或 Godot 复现步骤检查。
- 多个任务之间不会同时修改同一个脚本、同一个场景或同一个文档。

常见适合任务：

- 检查某个目录或模块的当前状态。
- 对照 spec 检查某个功能有没有实现。
- 按主 Agent 指定范围实现一个独立功能。
- 为一个独立功能设计测试用例。
- 调查一个失败测试、报错或日志问题。
- 检查 Godot 场景、脚本和资源引用是否一致。
- 对照画面基准和真实截图做视觉验收。
- 复核实现是否满足验收标准。
- 复核代码质量和项目结构是否符合本项目规则。

## 什么时候不要开子 Agent

以下情况不要急着开子 Agent：

- spec 还没读清楚，验收标准还没定。
- 任务边界很模糊，只知道“大概做一个功能”。
- 任务需要决定玩法规则、数值边界、产品取舍或目录结构。
- 多个子任务都会改同一个 `.gd`、`.tscn`、`.tres` 或同一个文档。
- 当前工作区有未确认的本地改动，可能被子 Agent 覆盖。
- 还没有测试、日志、截图或复现步骤，无法判断结果是否正确。
- 问题看起来分散，但很可能来自同一个根因。

如果任务不清楚，主 Agent 要先自己补上下文，必要时先写验收标准和测试方案，再决定是否拆给子 Agent。

## 开子 Agent 前必须准备的信息

主 Agent 派发任务前，要先准备下面这些信息。不要让子 Agent 自己猜。

- 本次任务来自哪个 spec 或哪条用户要求。
- 本次任务对应哪些验收标准。
- 子 Agent 的具体目标是什么。
- 子 Agent 可以查看哪些文件。
- 子 Agent 可以修改哪些文件。
- 子 Agent 不能修改哪些文件。
- 完成后必须返回哪些内容。
- 用什么方式验证结果。

如果是开发任务，还要说明：

- 是否允许修改 Godot 场景。
- 是否允许新增资源。
- 是否允许改测试工具。
- 是否必须提供截图、日志或测试输出。

如果是视觉校对任务，还要说明：

- 要对照哪份画面基准、素材说明或参考截图。
- 要检查哪张真实运行截图、哪段帧序列或哪段录屏。
- 本次重点看 HUD、升级界面、结算界面、战斗场景还是 VFX。
- 缺少哪些证据时必须判为不通过。

## 子 Agent 任务写法

给子 Agent 的任务要小、清楚、可检查。

推荐写法：

```md
任务：检查玩家移动逻辑是否满足验收标准。

背景：
- 项目是 Godot 4.x + GDScript 2D 游戏。
- 当前验收标准在 `docs/player-movement-acceptance.md`。

范围：
- 可以读取 `scripts/player_controller.gd` 和相关测试文档。
- 不要修改代码。
- 不要修改场景。

目标：
- 对照验收标准逐条检查。
- 列出已满足、未满足和无法判断的项目。

返回：
- 简短结论。
- 逐条检查结果。
- 需要主 Agent 决定的问题。
```

开发任务可以这样写：

```md
任务：实现升级卡片弹窗的运行时 UI。

背景：
- spec 在 `spec/v0.1-戴夫突围.md`。
- 验收标准在 `docs/development/acceptance-standard.md`。
- 测试用例在 `docs/v0.1-test-cases.md`。

范围：
- 可以修改 `scripts/`、`scenes/` 和必要的 `assets/` 运行时资源。
- 不要修改验收标准。
- 不要修改测试口径。
- 不要重构无关玩法逻辑。

目标：
- 升级三选一居中弹出，战场压暗。
- 卡片结构对齐画面基准。
- 提供真实运行截图或帧序列。

返回：
- 改了哪些文件。
- 如何运行验证。
- 哪些验收标准被覆盖。
- 是否还有没覆盖的测试点。
```

视觉校对任务可以这样写：

```md
任务：对照基准图复核升级三选一界面。

背景：
- spec 在 `spec/v0.1-戴夫突围.md`。
- 验收标准在 `docs/development/acceptance-standard.md`。
- 画面基准是 `docs/references/upgrade-baseline.png`。
- 真实运行截图是 `reports/visual/upgrade-current.png`。

范围：
- 只读。
- 不要修改代码、场景、资源或文档。

目标：
- 对照基准检查弹窗位置、战场压暗、三卡比例、卡片结构、装饰层级、材质风格和文字可读性。
- 按 P0/P1/P2 列出视觉问题。

返回：
- 通过 / 不通过。
- 每个问题对应哪条验收标准或哪张基准图。
- 缺少哪些截图、帧序列或观察证据。
```

不要这样写：

- “把整个功能做完。”
- “检查一下有没有问题。”
- “优化所有代码。”
- “根据 spec 全部实现。”

这些任务太大，子 Agent 容易跑偏。

## 推荐协作流程

如果要让子 Agent 参与开发，主 Agent 按这个流程走：

1. 主 Agent 先阅读 spec。
2. 主 Agent 写出或确认验收标准。
3. 主 Agent 写出或确认测试用例。
4. 主 Agent 判断哪些任务可以独立拆分。
5. 主 Agent 给每个子 Agent 一份完整、边界清楚的任务说明。
6. `builder` 完成实现后，主 Agent 先复核是否满足验收标准。
7. 涉及画面的改动，先交给 `visual-reviewer` 对照真实截图和基准图做只读复核。
8. 验收标准和必要的视觉复核通过后，再交给 `reviewer` 做综合复核。
9. 如果发现问题，主 Agent 明确指出问题，并安排修复。
10. 所有子任务完成后，主 Agent 统一运行测试或检查。
11. 最终汇报由主 Agent 给出，不直接照搬子 Agent 结论。

## 并行规则

可以并行的情况：

- 多个子 Agent 都是只读调查。
- 多个子 Agent 检查不同目录、不同文档或不同失败点。
- 多个任务之间不会修改同一批文件。
- 每个任务都有独立验证方式。

不要并行的情况：

- 多个子 Agent 会修改同一个脚本。
- 多个子 Agent 会修改同一个 Godot 场景。
- 多个子 Agent 会同时改 `docs/index.md`、AGENTS.md 或同一份 spec。
- 一个任务的结果会决定另一个任务怎么做。
- 当前问题可能来自同一个根因，需要先统一分析。

并行任务结束后，主 Agent 必须统一检查改动，确认没有互相覆盖、重复实现或风格不一致。

## 子 Agent 返回格式

子 Agent 完成后，必须用简短清单返回：

- 做了什么。
- 改了哪些文件。
- 怎么验证。
- 是否完全满足任务要求。
- 还存在哪些不确定点或风险。

如果没有完成，必须说明：

- 卡在哪里。
- 已经查过什么。
- 为什么继续不下去。
- 需要主 Agent 补什么上下文。
- 下一步建议怎么做。

## 复核规则

主 Agent 不能只相信子 Agent 的结论。至少要做这些复核：

- 检查子 Agent 是否超出任务范围。
- 检查是否改了不该改的文件。
- 对照验收标准逐条确认。
- 对照测试用例确认覆盖情况。
- 查看关键 diff，确认没有顺手重构无关内容。
- 运行相关测试、检查脚本或 Godot 验证步骤。
- 如果改了文档，确认 `docs/index.md` 已更新。

如果子 Agent 做的是代码实现，主 Agent 要先做验收标准复核，再做代码质量复核。验收标准没过之前，不进入代码质量复核。

如果子 Agent 做的是画面实现，主 Agent 要先确认有真实截图、帧序列或录屏，再交给 `visual-reviewer`。没有可观察证据时，不进入视觉通过判断。

## Godot 项目特别规则

- 不得替换 Godot 作为游戏主体。
- 不得把核心游戏逻辑搬到外部脚本里。
- 修改 `.tscn`、`.tres`、资源引用或 Godot 导入文件时，必须说明影响范围。
- 涉及画面、碰撞、输入、关卡状态或资源加载时，必须提供可观察的验证方式。
- 外部脚本只能用于资源处理、检查和辅助验证，不能承载核心游戏逻辑。
- 场景和脚本改动要尽量小，不要顺手重构无关内容。

## 一句话判断

开子 Agent 前先问一句：这个任务能不能用清楚的范围、输入、输出和验证方式交代明白？

如果答案是能，可以开。

如果答案是不能，主 Agent 先把问题拆清楚。
