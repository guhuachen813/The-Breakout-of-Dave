## 文档职责

本文档把本轮新增需求转成可执行、可观察、可复核的测试用例。本文档只定义测试和证据要求，不写产品实现，不修改 `docs/development/acceptance-standard.md`，不替 `spec/` 或素材文档另立口径。

## 依据

- 当前验收标准：`docs/development/acceptance-standard.md`
- 本轮新增功能事实源：用户需求文本
- 既有 v0.1 事实源：`spec/游戏机制.md`、`spec/视觉规格.md`、`spec/v0.1-戴夫突围.md`
- 音频素材边界：`assets/audio/README.md`、`assets/audio/LICENSES.md`
- 现有验证入口：Godot 命令行运行主场景，使用 `--debug-mode`、`--validation-report`、`--capture-dir`、`--run-seconds`、`--time-scale`、`--auto-upgrade`、`--auto-play`

## 测试入口规划

本轮要求实现方补齐下面的调试入口和报告字段。本文档只提出测试要求，不实现这些入口；这些入口、截图和 `validation_report` 字段未落地前，对应测试不算通过。

| 入口 | 用途 | 必需证据 |
| --- | --- | --- |
| `--debug-mode=menu_probe` | 启动到开始界面，自动枚举按钮、打开开发团队页和成绩页。 | `validation_report.menu_probe`、`capture_dir/menu_start_normal.png`、`capture_dir/menu_developers_normal.png`、`capture_dir/menu_scores_empty_normal.png` |

需要截图的用例使用真实窗口或可保存 viewport 的运行方式：

## MSB-TC-01 开始界面入口与开发者署名

目的：确认游戏启动先出现开始界面，开始界面提供“开始游戏”“成绩”“开发团队”，点击“开发团队”后显示 aya 和 HexBlank，且一行一个名字。

覆盖需求：R-MSB-01

覆盖 AC：AC-LOOP-01、AC-INPUT-05、AC-UI-03、AC-UI-05、AC-OBS-04

前置条件：

- 实现方补齐 `--debug-mode=menu_probe`。
- `menu_probe` 能导出开始界面、开发团队页、成绩页的 UI 状态快照和截图，并记录开发者姓名展示方式。

操作步骤：

1. 使用 `--debug-mode=menu_probe --validation-report=... --capture-dir=...` 启动主场景。
2. 在未点击任何按钮时保存开始界面截图 `menu_start_normal.png`。
3. 在报告中记录开始界面可点击项文本、可见性、可用状态和当前游戏状态。
4. 自动点击或调用“开发团队”入口，保存 `menu_developers_normal.png`。
5. 返回开始界面后自动点击或调用“成绩”，保存成绩页截图。

自动断言：

- `validation_report.game_state` 或 `validation_report.menu_probe.current_screen` 表示当前处于开始界面，不直接进入战斗。
- `validation_report.menu_probe.start.buttons` 精确包含中文文本“开始游戏”“成绩”“开发团队”。
- 三个入口均 `visible == true` 且 `enabled == true`。
- `validation_report.menu_probe.developers.names` 精确包含 `aya` 和 `HexBlank`，且不缺字、不改大小写。
- `validation_report.menu_probe.developers.display_mode == "developer_team_screen"`。
- `validation_report.menu_probe.developers.names_layout == "one_per_line"`。
- `validation_report.menu_probe.start.unexpected_completion_texts` 为空；画面不出现“已完成需求”等验收说明文字。

视觉复核：

- `menu_start_normal.png` 和 `menu_developers_normal.png` 中按钮、标题、姓名不重叠、不裁切，标题和姓名均位于面板内容区内。
- UI 文案为中文；开发者姓名按事实源保留英文大小写。
- 正常截图中无调试辅助层痕迹。

## MSB-TC-02 “开始游戏”进入战斗闭环

目的：确认点击“开始游戏”后进入正常一局，不破坏 v0.1 从开始到战斗、结算、重玩的闭环。

覆盖需求：R-MSB-01

覆盖 AC：AC-LOOP-01、AC-INPUT-05、AC-RUN-02、AC-OBS-02

前置条件：

- 实现方补齐 `--debug-mode=menu_probe` 的开始按钮自动操作。
- 状态快照保留 `game_state`、`game_time`、`current_wave`、`player_hp`、`unlocked_weapons` 等既有字段。

操作步骤：

1. 使用 `menu_probe` 启动开始界面。
2. 自动触发“开始游戏”。
3. 运行 5 秒游戏时间。
4. 导出 `after_start_game` 状态快照。

自动断言：

- 点击前状态为开始界面；点击后状态为 `combat` 或等价战斗状态。
- `after_start_game.game_time > 0`。
- `after_start_game.current_wave == 1`。
- `after_start_game.player_hp == 100`。
- `after_start_game.unlocked_weapons` 仅包含开局武器橘豌豆。
- 日志中没有脚本解析错误、资源加载错误或运行时致命错误。

## MSB-TC-03 成绩页空状态与最高 10 个分数

目的：确认成绩页在没有成绩时显示“？？?”；有成绩时只显示最高 10 个分数，并按分数高低稳定排序。

覆盖需求：R-MSB-03

覆盖 AC：AC-UI-03、AC-UI-05、AC-OBS-02、AC-OBS-04、AC-RUN-06

前置条件：

- 实现方补齐 `--debug-mode=scores_probe`。
- `scores_probe` 支持清理本地成绩、注入至少 12 条可控成绩样本、写入本地持久化成绩、重启 Godot 后再次读取成绩。
- `validation_report.scores_probe` 必须包含 `persistence_path`、`cleanup_method`、`cleanup_result`、`written_scores`、`restart_evidence`、`loaded_scores_after_restart`、`uses_account_or_backend`。
- `restart_evidence` 必须能证明写入和读取发生在两次独立启动中，例如包含两次运行的 `run_id`、进程号、启动时间或等价可区分字段。

操作步骤：

1. 以空成绩状态运行 `scores_probe`，打开成绩页并保存 `menu_scores_empty_normal.png`。
2. 读取 `validation_report.scores_probe.empty_state`。
3. 注入 12 条乱序成绩，例如 `100, 900, 300, 700, 1100, 500, 200, 800, 400, 1000, 600, 1200`。
4. 打开成绩页并保存 `menu_scores_top10_normal.png`。
5. 读取 `validation_report.scores_probe.displayed_scores`。
6. 结束当前 Godot 进程后重新启动项目，使用同一个本地持久化路径读取成绩。
7. 导出 `validation_report.scores_probe.loaded_scores_after_restart` 和 `restart_evidence`。

自动断言：

- 空成绩时 `empty_placeholder == "？？?"`，且 `displayed_scores` 为空。
- 有成绩时 `displayed_scores.size() == 10`。
- `displayed_scores` 精确等于注入成绩中的前 10 个最高分，按降序排列：`[1200, 1100, 1000, 900, 800, 700, 600, 500, 400, 300]`。
- 不显示第 11、12 名分数 `200`、`100`。
- `validation_report.scores_probe.uses_account_or_backend == false`；不得把本地成绩页实现成账号、后端或在线排行榜功能。
- `persistence_path` 非空，指向本地项目或 Godot 用户数据路径，不是网络地址。
- `cleanup_method` 非空，且 `cleanup_result.success == true`。
- `written_scores` 包含本次注入的 12 条成绩。
- `restart_evidence.first_run_id != restart_evidence.second_run_id`，或提供等价证据证明发生过独立重启。
- `loaded_scores_after_restart` 至少包含写入后的最高 10 个分数，且前 10 名与 `displayed_scores` 一致。
- `uses_account_or_backend == false`；报告中不得出现账号登录、远程 API、在线排行榜、服务端地址或网络同步字段。

视觉复核：

- 空成绩截图中能清楚看到“？？?”。
- 前 10 名分数在 `menu_scores_top10_normal.png` 中不重叠、不裁切。
- 成绩页不出现验收说明文字或调试辅助层。

通过限制：

- `scores_probe`、持久化字段、清理字段、重启读取证据任一缺失时，R-MSB-03 不算通过。

## MSB-TC-04 失败结算分数、破纪录、退出与重玩

目的：确认戴夫死亡后进入失败结算，显示本局分数和是否破记录，并提供“退出”“重玩”两个选项；“退出”只能触发退出进程请求。

覆盖需求：R-MSB-02

覆盖 AC：AC-LOOP-02、AC-LOOP-05、AC-LOOP-06、AC-INPUT-05、AC-UI-03、AC-UI-05、AC-OBS-03、AC-OBS-04

前置条件：

- 实现方补齐 `--debug-mode=failure_score_probe`。
- `failure_score_probe` 能注入或构造两次失败：一次非破纪录，一次破纪录。
- 报告字段包含失败前分数、历史最高分、是否破纪录、按钮文本、重玩后初始状态、退出进程请求结果。

操作步骤：

1. 使用 `failure_score_probe` 快速进入死亡失败流程。
2. 保存失败结算截图 `result_failure_score_normal.png`。
3. 导出 `validation_report.failure_score_probe.first_failure`。
4. 触发“重玩”，导出 `after_replay` 状态快照。
5. 再构造更高分失败，导出 `record_failure`。
6. 触发“退出”，记录退出进程请求。自动探针允许拦截真实 `quit` 以便写出报告，但必须记录拦截到的退出请求。

自动断言：

- 死亡后 `game_state == "failure"` 或等价失败状态。
- 失败结算按钮文本精确包含“退出”和“重玩”。
- 失败结算展示的分数字段为数值型，且与报告中的 `score` 一致。
- 非破纪录样本 `is_new_record == false`；破纪录样本 `is_new_record == true`。
- “重玩”后 `player_hp == 100`、`current_wave == 1`、`game_time == 0`、`kills == 0`、`upgrade_count == 0`、`unlocked_weapons` 回到开局状态。
- “退出”触发明确事件 `exit_requested == true`。
- 如果自动探针拦截真实退出，必须记录 `quit_intercepted == true` 和被拦截的退出请求来源。
- `returned_to_start_menu_after_exit == true` 不能作为通过证据；如果点击“退出”只是返回开始界面且没有退出进程请求，本用例不通过。

视觉复核：

- `result_failure_score_normal.png` 中能看见失败标题、分数、破纪录状态、“退出”“重玩”。
- 分数、破纪录文案、按钮和既有结算统计不互相遮挡、不裁切。
- 结算面板仍满足居中弹出和中文 UI 要求。

通过限制：

- `failure_score_probe`、失败截图、分数字段、破纪录字段、退出进程请求字段任一缺失时，R-MSB-02 不算通过。
- 本轮测试不自行规定分数公式，只要求分数为一致的数值型结果，并通过受控样本验证记录比较。

## MSB-TC-05 BGM 提取、替换与运行时加载

目的：确认背景音乐来自指定 MP4 提取音频，运行时加载成功并作为背景音乐播放，不继续使用旧背景音乐或空音频。

覆盖需求：R-MSB-04

覆盖 AC：AC-RUN-02、AC-RUN-03、AC-FEEDBACK-06、AC-OBS-02

前置条件：

- 实现方补齐 `--debug-mode=bgm_probe`。
- 实现方从 `/Users/wawa/Downloads/39995331_da2-1-16.mp4` 提取音频并接入 Godot 运行时资源。
- BGM 运行时路径固定为 `res://assets/audio/sfx/background_bgm_01.ogg`，或同目录 `res://assets/audio/sfx/` 下的项目内音频文件。
- 实现方必须更新 `assets/audio/README.md`，记录指定 MP4 来源和运行时文件映射；`assets/audio/LICENSES.md` 不要求记录用户提供的 BGM 映射。本测试只验证记录存在，不修改素材文档。

操作步骤：

1. 运行 `bgm_probe`，导出 `validation_report.bgm_probe`。
2. 扫描运行时音频路径、加载日志和 `assets/audio/README.md`。
3. 启动战斗状态至少 5 秒，记录 BGM 播放状态。
4. 如支持音频事件日志，记录 `bgm_started`、`bgm_loop_enabled` 或等价字段。

自动断言：

- `bgm_probe.source_input_path == "/Users/wawa/Downloads/39995331_da2-1-16.mp4"`。
- `bgm_probe.runtime_path == "res://assets/audio/sfx/background_bgm_01.ogg"`，或 `bgm_probe.runtime_path` 指向 `res://assets/audio/sfx/` 下的项目内音频文件。
- `bgm_probe.runtime_path` 不能直接引用 `/Users/wawa/Downloads/39995331_da2-1-16.mp4`，也不能指向 `assets/source/`、项目外路径或非 `assets/audio/sfx/` 目录。
- `bgm_probe.stream_loaded == true`。
- `bgm_probe.stream_length_seconds > 0`。
- `bgm_probe.playing_in_combat == true`。
- `bgm_probe.is_silent_placeholder == false`。
- `bgm_probe.replaced_previous_bgm == true`，或报告中能证明当前唯一 BGM 为本轮提取音频。
- `bgm_probe.audio_readme_contains_source_record == true`，且 `assets/audio/README.md` 中可找到 `39995331_da2-1-16.mp4` 和运行时 BGM 文件名。
- `bgm_probe.audio_licenses_omits_user_bgm_mapping == true`，即 `assets/audio/LICENSES.md` 不记录用户提供的 BGM 映射。
- `sfx_missing` 为空，且新增 BGM 不破坏既有 SFX 加载。
- 运行日志没有资源加载错误、解码错误或运行时致命错误。

人工或工具复核：

- 音频授权和来源记录已更新到音频文档，且能追溯到指定 MP4。
- 运行时资源路径位于 `assets/audio/sfx/`，符合 AC-RUN-03 的运行时音频目录口径。

通过限制：

- `bgm_probe`、运行时路径断言、音频加载断言、`assets/audio/README.md` 记录任一缺失时，R-MSB-04 不算通过。
