# Harness 原则整理

本文整理两篇 harness 文章中对本仓库有用的原则，并把它们改写成《戴夫突围》开发时可执行的规则。

来源：

- OpenAI, [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/), 2026-02-11
- Anthropic, [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-03-24

## 核心判断

Harness 不是一个更长的提示词，而是一套让 AI 代理能持续做正确工作的环境：清楚的目标、可读的仓库知识、可执行的验收标准、可观察的运行状态、能失败的测试、真实画面证据，以及能把错误沉淀回仓库的反馈循环。

对本项目来说，harness 的目标不是让代理一次性写出更多代码，而是让代理每次都能知道：

1. 现在要做的最小闭环是什么。
2. 哪些范围明确不做。
3. 游戏运行时的真实状态如何读取。
4. 功能、美术、音频和 UI 是否真的达标。
5. 失败时要补哪种工具、文档、规则或测试。

## 原则清单

### 1. 人负责方向，代理负责执行和取证

人类要定义目标、边界、验收口径和主观取舍；代理负责拆任务、写代码、跑检查、保存截图、记录证据和修复失败。

当代理卡住时，不要只让它“再试一次”。应该问：缺的是可读状态、明确规则、测试入口、素材说明、运行截图，还是更具体的完成标准。

### 2. 仓库是事实来源

对代理不可见的知识，等于不存在。游戏规则、素材接入、验收标准、测试命令、经验规则和交付记录都应写入仓库，而不是只留在聊天记录、外部文档或人的记忆里。

`AGENTS.md` 应作为入口目录，指向更深的文档；不要把所有细节塞成一个巨大手册。长文档要拆成稳定主题，并让代理按任务需要逐步读取。

### 3. 先让系统可观察，再扩展玩法

复杂任务要先建立反馈回路。对本项目，优先级是：

1. 固定 seed。
2. debug 参数。
3. `get_debug_snapshot()`。
4. `get_recent_feedback_events()`。
5. smoke test。
6. 真实截图、动态帧或可视窗口检查。
7. 交付记录和 Experience Library 更新。

没有这些观测点，代理会把“代码看起来合理”误判成“游戏真的可玩”。

### 4. 把大任务拆成可验收的小块

长时间开发不能靠一个模糊目标连续推进。每一块工作都要先写清楚：

- 本轮要交付什么。
- 不交付什么。
- 哪些状态、事件、截图或动态帧能证明它完成。
- 哪些 smoke 参数会失败或通过。

Anthropic 文章里的 planner / generator / evaluator 结构，可以简化成当前仓库的工作方式：先定本轮契约，再实现，再用独立验收标准检查。范围较大时，把契约写进文档或交付记录，方便下一轮继续。

### 5. 生成者和评估者要分离

代理很容易高估自己刚完成的工作，尤其是 UI、视觉、手感这类主观任务。实现完成后，验收要站在“挑错”的角度执行，而不是让同一段总结文字自我认可。

本项目的评估者至少要检查：

- 功能是否真实跑通。
- UI/VFX 是否使用定制资产，而不是占位图或原素材切片。
- 逐控件相似度和完成度是否都达到 0.90。
- 动态帧里是否有遮挡、重叠、裁切、跳位或不可点击。
- 音频是否真实加载并在事件中触发。

### 6. 把主观质量变成可评分标准

“好看”“有手感”“像参考图”不能直接作为验收。要把它们拆成可记录的标准：

- 参考 crop。
- 视觉特征拆解。
- 最终资产路径。
- 运行截图 crop。
- 并排对照图。
- `style_similarity_score`。
- `asset_completion_score`。
- 动态帧观察结论。

这和 Anthropic 文章中把前端审美拆成设计质量、原创性、工艺和功能性相同：主观判断不能完全消失，但必须被拆成代理能执行、能复查的检查项。

### 7. 验证必须操作真实应用

代码审查和 headless smoke 只能证明一部分事实。涉及 UI、布局、动画、特效、音频和玩法手感时，必须让代理启动真实游戏或可渲染画面，保存截图、frame dump 或短录屏。

本项目不能只用控件坐标、日志或 “SMOKE_TEST_PASS” 宣称 UI 完成。真实画面里有遮挡、裁切、默认控件、特效压住 UI 或中文文案不一致时，验收失败。

### 8. 用硬边界保护架构和范围

代理适合在明确边界内高速执行，不适合在边界模糊时自行扩大产品。仓库应机械地或文档化地守住这些边界：

- 游戏规则不写死在 UI、动画或特效脚本里。
- 输入、战斗、刷怪、升级、结算分开。
- 不引入后端、数据库、账号、排行榜或多人联机。
- 不做复杂主菜单、剧情、商店、背包、Boss、多关卡和存档。
- 素材只能使用当前工作树内的文档、素材和代码。

架构规则应尽量通过测试、脚本、资源审计和清晰错误信息执行；不能只靠口头提醒。

### 9. 长任务需要结构化交接

当任务跨多轮、上下文变长或需要暂停时，必须把当前状态写入仓库内的交付记录、实验日志或计划文档，至少包含：

- 已完成的验收项。
- 未完成的验收项。
- 已跑命令和结果。
- 关键截图或动态帧路径。
- 发现的问题。
- 下一步最小任务。

上下文压缩或新会话不是问题，问题是没有足够清楚的交接文件让下一轮代理接住工作。

### 10. Harness 复杂度要定期清理

每个 harness 组件都代表一个假设：当前模型自己做不好这件事，所以需要额外脚手架。模型、项目和工具变了之后，这个假设可能失效。

因此不要盲目增加流程。新增测试、文档、评估代理、截图门禁或脚本前，要说明它解决了什么实际失败。后续如果它不再提供价值，应删除、合并或简化。

### 11. 错误要沉淀成规则

代理会复用仓库里已有模式，坏模式也会被复制。解决过的问题不能只留在最终回复里，应该写入：

- `docs/experience-library/lessons.md`：完整记录现象、原因、修复、验证和下次规则。
- `docs/experience-library/active-rules.md`：容易复发的问题提炼成短规则。

这相当于把一次人工判断转成后续每轮都能读取的约束。

## 本仓库的默认工作流

每轮开发按下面顺序执行：

1. 按 `AGENTS.md` 读取上下文。
2. 明确本轮最小目标和不做范围。
3. 写清楚本轮验收入口：命令、状态字段、反馈事件、截图或动态帧。
4. 先补缺失的可观测性，再扩展玩法或视觉。
5. 实现一个小块后立即运行可用检查。
6. UI/VFX/音频相关改动必须保存真实画面或事件证据。
7. 失败时补工具、测试、文档或规则，不用猜测替代验证。
8. 解决过的问题写入 Experience Library。
9. 提交前只 stage 本轮相关文件，并运行 `git diff --check`。

## 不要做的事

- 不把参考文章改写成一篇长理论文档后就停止。
- 不把所有规则继续堆进 `AGENTS.md`。
- 不用聊天记录代替仓库文档。
- 不用 headless 输出代替 UI/VFX 的真实画面检查。
- 不让实现者只靠自我总结判定通过。
- 不为了让测试通过而降低验收标准。
- 不在缺少 seed、snapshot、事件和截图能力时扩展更多玩法。
- 不在没有明确失败案例时增加复杂 harness 组件。
